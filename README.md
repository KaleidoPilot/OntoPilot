# KaleidoPilot 后端

公司内部用的 AI 问答与数据分析平台，后端部分，基于 FastAPI。前端在另一个仓库（Vue 3），这里只放接口服务。

一句话概括：把「技能」「知识库」「业务数据」「外部工具」拼在一起，让用户用自然语言提问，系统自己决定查哪份资料、跑哪段代码，最后把结果整理成人能看的内容。

## 两个核心设计

这个项目跟「接个大模型问一句答一句」不太一样，有两块下了功夫的设计：**业务数据在客户沙箱里算，最后一步的总结模型可以换成本地模型**；**知识库除了向量检索还有一整套知识图谱**。下面把流程讲清楚。

## 特色一：代码在沙箱里跑，总结模型可替换

### 为什么这么设计

让模型直接连业务数据库是不行的：连接串交给模型等于泄露凭据，模型也可能写出 update、delete 这类语句。所以这里做了拆分——**模型只负责生成代码，代码在客户自己的沙箱里执行，执行完的文本结果再交给总结模型写报告**。

四个环节各用一个模型，互相独立配置：

| 环节 | 干什么 | 会看到什么 |
| --- | --- | --- |
| 意图模型 | 判断这个问题该用哪个技能 | 用户问题、技能清单 |
| 任务拆分模型 | 把问题拆成几步可执行的查询任务 | 用户问题、表结构、表关系、技能规则 |
| 代码执行模型 | 生成 Python + SQL，交给沙箱跑 | 用户问题、表结构、技能规则 |
| 总结模型 | 把执行结果整理成业务报告 | 用户问题、**查询出来的业务数据** |

重点在最后一行：**只有总结模型这一步会看到真实业务数据**。前三步传给模型的是问题、表结构（字段名、类型、注释）和技能规则，不含查出来的数据。

所以数据敏感的场景，把总结模型换成内网私有化部署的模型就行——vLLM、Ollama、Xinference 这类 OpenAI 兼容服务都能接，业务数据不出内网；前三步还可以继续用效果更好的云端模型。四个模型在技能配置里是四个独立字段（`intentLlmId`、`taskLlmId`、`executLlmId`、`summaryLlmId`），想全换成本地的也可以，改配置不改代码。

### 一次提问的完整流程

以「查一下上个月各品类的销售额和毛利率」为例：

1. **匹配技能组**。前端先按用户组拿到可用技能组；Auto 模式下调 `/group/skill-groups/match`，由模型从候选组里挑一个，手动选了技能组就跳过这步。
2. **匹配主技能**。把技能组内所有主技能的名称和描述给意图模型，让它选出最合适的一个并返回技能 ID。选不出来就走知识库兜底回答，不会报错。
3. **解析技能家族**。主技能配了子技能的话，子技能才是实际执行单元，主技能只提供口径和编排方式；没配子技能就它自己执行。同时把主技能的公共数据表和各子技能的数据表合并去重。
4. **定位沙箱**。用这批数据表反查所属项目组，再取项目组绑定的沙箱配置。**要求所有表来自同一个沙箱**，跨数据源直接报错，避免一次请求连到两个客户库。然后向沙箱要一个可用内核，没有就新建。
5. **加载表结构与表关系**。从平台库读已导入的字段快照（字段名、类型、中文名、备注）和人工确认过的表关联关系，一起放进模型上下文。模型只能依据这些真实字段写 SQL，不许猜字段名。
6. **判定编排方式**。把主技能规则交给模型判断：规则里写了「先…再…」就串行，没写先后就并行。串行时前一步的结果作为参考写进下一步的上下文；并行时每个子技能开独立协程，日志通过队列实时回传，前端能同时看到几条流。
7. **执行单元内部循环**（每个子技能各跑一遍）：
   - 任务拆分模型把问题拆成若干步，每步一个明确的查询目标；
   - 代码执行模型为每一步生成 Python 代码，代码通过沙箱预置的 `get_connection()` 拿数据库连接，只允许 `SELECT`，条件值必须参数绑定；
   - 代码提交到沙箱内核执行，`print` 出来的文本表格就是这一步的结果；
   - 执行报错会把错误信息回传给模型自动修复重试，重试次数用完就如实报错，不拿空结果糊弄；
   - 需要给下一步传值时代码里 `print('__HANDOFF__' + json.dumps(...))`，下一步从衔接字典按 key 取。
8. **汇总总结**。所有执行单元的结果拼成一份家族结果，连同主技能规则口径、技能组设定、知识图谱基础事实、当前系统时间一起交给总结模型，输出最终的 Markdown 报告。要求数据一律表格化、分析必须给出数据依据、屏蔽 SQL 和表名等技术细节。
9. **全程流式**。上面每一步的进度都以 SSE 事件推给前端，执行日志放在可折叠的 `<details>` 块里，最后才是总结正文。

### 沙箱执行的硬约束

一部分写在代码执行模型的系统提示词里，一部分在执行层做拦截：

- 只读 `SELECT`，禁止任何写操作；条件值必须 `cursor.execute(sql, params)` 参数绑定。
- 严禁模型自己定义 `get_connection()`。代码里出现这个定义会被识别出来并要求重写，避免占位实现覆盖掉沙箱注入的真实连接。
- 数据库凭据由平台业务层拼进执行载荷，只发给沙箱，**不进模型上下文**；这类载荷走 strict 模式，不写入共享内核历史。
- MySQL 的 `DECIMAL` 列在 Python 里是 `decimal.Decimal`，和 `float` 直接混算会抛异常，提示词明确要求先转 `float` 再算。
- 用户给的商品编码、名称、规格不一定和库里一致，要求先用 `LIKE` 模糊探查确认命中再精确查；查出 0 行必须换匹配方式重试，不许直接返回空结果。
- 结果必须 `print` 成纯文本表格，不能只出图表；空结果如实说明。
- 每步在独立命名空间执行，用完 `rollback` 并关闭连接。

## 特色二：知识图谱

### 图谱解决什么问题

纯向量检索本质是「找相似的段落」，遇到跨文档的关联问题就不够用了，比如「甲项目和乙项目的验收分别到哪一步」「这份合同的付款争议涉及哪几方」。这类问题得先把资料里的人、组织、合同、事项抽成实体和关系，再顺着关系找答案。

平台在向量检索之外，给每个知识库单独建一套实体关系图谱，底层用 LightRAG。

### 建图流程

1. 前端点「建立图谱」，后端取出这个知识库当前全部文档的正文。
2. 算一份文档指纹（内容加文档 ID 的摘要）和上次比对。已经是 `ready` 且指纹没变就直接返回旧图，不重复花钱。
3. 检查公司有没有配好图谱需要的基础模型和 Embedding 模型，没配直接报明确的错。
4. 状态置 `building` 写库，起后台协程异步建图，接口立刻返回，前端轮询进度。
5. **在独立子进程里跑 LightRAG**。父进程只用标准库，起一个隔离的 Python 环境（由 `TEMPLATE_LIGHTRAG_PYTHON` 指定），请求和结果都通过 stdin/stdout 传 JSON。两个好处：模型密钥只存在于子进程内存，不会落到命令行、索引文件或日志里；LightRAG 及其依赖不会污染主项目环境。
6. 子进程按 4000 token 分片，逐份插入并确认处理完成，再抽取实体和关系。抽取时挂了一大段约束提示词，核心几条：只有原文明示的简称或编号对应才做实体归一化，不凭名称相近合并；同名人员按「姓名（单位·角色）」区分，不同项目的同名事项必须是不同实体；关系描述要写清谁对谁、做了什么、原文是什么状态，「计划验收」「部分已付」「单方主张」这类措辞不许简化成「已完成」「已付清」；有更正或撤回的要保留版本关系。
7. 抽取完做一致性校验：每个实体和关系必须能对回具体的原文块，对不上就报错，不允许出现没有出处的节点。
8. 再校验一次文档指纹。建图期间资料被人改过就判定失败，要求用当前资料重建，不拿旧资料的结果冒充。
9. 图谱快照（节点、关系、原文证据）写进 MySQL，建图用的临时工作目录直接删掉，不在磁盘上留索引。
10. 成功置 `ready`，失败置 `failed` 并记下原因。全程用文件锁保证同一个知识库不会并发建两份。

图谱有五种状态：`empty`（没文档）、`not_created`（没建过或资料已变）、`building`、`ready`、`failed`。

### 图谱问答流程

1. 收到问题先查状态，不是 `ready` 或指纹对不上，直接提示需要重建。
2. **在服务端本地做召回，不调模型**：把问题切成词（英文按单词，中文按 2-3 字滑窗，过滤掉「什么」「哪些」这类虚词），给节点和关系打分，取 Top 8 个种子节点、60 条关系、120 个节点，再顺着关系做一跳扩展，只保留两端都在上下文里的关系。
3. 按 48000 字节预算组装上下文，**先塞原文片段再塞节点关系**——不能只给模型图谱描述却不给核对依据。原文从命中位置往前 400 字开始截 3000 字，避免长文档只取开头漏掉被问的事实。每条原文标 `S1`、`S2`，每条关系标 `R1`、`R2`。
4. 调公司配的基础模型回答，要求只返回 `{"answer": "...", "sourceIds": ["S1"]}`，答案里每句话都要带原文编号。
5. **服务端校验模型输出**：`sourceIds` 里出现不在允许集合内的编号、答案引用了没给过的 `S#` 或 `R#`、答案超过 20000 字，一律判为协议错误直接拒绝，不让编造的引用流到前端。
6. 再比一次指纹，问答期间资料或图谱变了就返回 409，要求刷新重问。
7. 每个实体和关系都能点开看对应的原文块，出处可追溯。

### 图谱在对话里的两条使用路径

- **知识库问答时作为「图谱参考」**：先做向量召回，再对确实命中资料的知识库查一次图谱。图谱回答里的内部编号会被去掉，只保留原文出处文件名，和 `[资料N]` 的编号体系分开，避免前端引用错乱。多个知识库共享一份超时预算，超时就跳过剩下的，不会因为图谱慢把整轮回答拖住。
- **技能总结时作为「基础事实」**：把技能绑定知识库的图谱节点和关系渲染成一段文字，放进总结模型的提示词里，用来校正业务概念和口径。提示词里明确写了「仅作参考，与执行结果或资料原文冲突时以后者为准」。

### 降级与并发

图谱属于辅助信息，任何环节出问题都不该让整轮对话失败。图谱没建立、资料已变化、引擎繁忙、问答超时、模型没配置——全部只记一条 warning 然后跳过，回答退化为只用向量召回的资料，或者只用模型自身知识。

并发上有限制：图谱引擎同时最多跑 2 个任务，超出的等 3 秒拿不到名额就返回「引擎繁忙，请稍后重试」；图谱问答同样最多 2 个并发。

## 其他功能

### 对话入口

- Auto 智能匹配：按问题自动选技能组，选不到就交给 KaleidoPilot 兜底回答，不报错。
- 知识库查询：固定入口，跳过技能组匹配和技能编排，只在该用户被授权的全部知识库里做向量召回。
- 指定技能组：直接跑该组的技能编排。

### 知识库与向量检索

- 支持 Word、Excel、PDF 上传，解析后切片写入 Milvus，查询时走向量召回，再用 rerank 排一遍。文档里的图片和图表目前只提示、不做识别，提取的是文字和表格。
- 回答带来源编号，能对回原始资料。
- 权限分三种：公司公开、公司私有（可授权到具体用户或用户组）、个人。内部用户和外部用户走同一套鉴权逻辑。
- 知识库和 Milvus 的数据可以手动触发同步修复。

### 数据项目组

- 接业务数据库，把表结构导入平台，字段中文名和备注都能维护。
- 导入表之后 AI 会推荐表之间的关联关系，人工确认后保存。
- 平台只存字段快照，不持有客户数据库的连接凭据，查询全部发生在客户沙箱里。

### MCP 工具

- 支持接入公司级和个人级的 MCP Server，读取工具列表，按技能粒度绑定具体工具。
- 有写操作的工具会走人工确认，前端弹出待确认操作，用户点同意才继续执行。
- 个人 MCP 的密钥单独加密保存，接口只返回脱敏信息。

### 模板技能与文档生成

- 上传一份写得不错的报告，系统提炼出写作规则，存成个人模板技能。
- 之后拿模板加本次资料生成新报告，支持导出 Markdown、DOCX、PDF。
- 任务异步执行，进度和日志可以轮询查看，失败能重试。

### 账号与多租户

- 公司、用户组、内部用户、外部用户、公司管理员、超级管理员这一套体系。
- 登录签发 JWT，MCP 调用单独签发访问令牌。
- 所有业务数据按公司隔离，查询层统一带 `ORG_ID` 条件。

### 其他

- 对话上下文：最近几轮原文直接带上，更早的对话压缩成一段摘要，避免长对话把上下文撑爆。
- 日志按大小轮转，默认写在 `logs/app.log`，日志级别在 `.env` 里改。
- 自带代码生成脚本，新增一张表时可以生成基础的增删改查接口：

```bash
python utils/code_generator.py --table 表名 --module 模块名
# 用到 Milvus 时加 --milvus
```

## 技术栈

| 用途 | 选型 |
| --- | --- |
| Web 框架 | FastAPI + Starlette，接口文档走 `/docs` |

| 向量库 | Milvus（pymilvus MilvusClient） |

| 运行环境 | Python 3.12 |

## 本地跑起来

### 1. 准备环境

- Python 3.12
- MySQL 5.7（`utf8mb4`）
- Milvus（知识库功能必需；不用知识库可以先不装，但相关接口会报错）
- Jupyter Kernel 网关（可选，只有需要执行代码的技能才用）

### 2. 安装依赖

```bash
conda create -n kaleido python=3.12
conda activate kaleido
pip install -r requirements.txt
```

### 3. 配置

环境相关的配置放在 `.env.test` 或 `.env.prod`，通过 `APP_ENV` 决定加载哪个：

```ini
APP_NAME="KaleidoPilot"
APP_ENV="test"
APP_HOST="0.0.0.0"
APP_PORT=9711
DEBUG=True
LOG_LEVEL="INFO"
LOG_FILE="app_test.log"
```

模型、Milvus、MySQL、沙箱的配置在 `config.yaml`：

```yaml
model_settings:
  llm:
    model: 你的模型名
    api_key: 你的密钥
    base_url: https://你的服务地址/v1
  embedding:
    model: 你的向量模型
    api_key: 你的密钥
    base_url: https://你的服务地址/v1
  rerank:
    model: 你的重排模型
    api_key: 你的密钥
    base_url: https://你的服务地址/v1

milvus_settings:
  host: 127.0.0.1
  port: 19530
  db_name: 你的数据库
  collection_name: user
  vector_dim: 1536      # 必须和 embedding 模型的输出维度一致
  index_type: IVF_FLAT

database_settings:
  db_type: mysql
  mysql:
    host: 127.0.0.1
    port: 3306
    user: 你的账号
    password: 你的密码
    db: ai_platform
    minsize: 1
    maxsize: 10
    db_version: "5.7"

sandbox:
  url: "http://127.0.0.1:7080"
  token: "你的沙箱令牌"
```

两个容易踩的点：

- `vector_dim` 和向量模型的实际维度必须一致，不一致写入会直接失败。换 embedding 模型后，旧向量要重新生成。
- `collection_name` 改了等于换了一个集合，历史数据不会自动迁移。

### 4. 建表

仓库没有附带完整的建库脚本。各模块的表结构定义在 `api/endpoints/*/sql/tables.py`，可以照着建；`api/endpoints/organization/sql/migration.sql` 是组织模块的迁移脚本。生产环境建议自己维护 DDL 或用迁移工具管理，不要靠手写临时 SQL。

### 5. 启动

```bash
python main.py
```

默认监听 `0.0.0.0:9711`，接口统一挂在 `/fijoAi` 前缀下，打开 `http://127.0.0.1:9711/docs` 能看到全部接口。

## 部署

### 方式一：直接跑进程（推荐）

```bash
# 生产环境建议关掉 reload
APP_ENV=prod python main.py
```

或者用 uvicorn 指定 worker：

```bash
uvicorn main:app --host 0.0.0.0 --port 9711 --workers 2
```

知识库上传的文件默认落在 `storage/knowledge/`，记得跟 `logs/` 一起挂到持久化目录。

### 方式二：Docker

仓库里的 `Dockerfile` 是两阶段构建：先在 builder 里用 conda 环境把源码编译成 `.pyc`，运行时镜像里只留字节码，不带源码。

注意它依赖一个仓库外的 conda 环境包 `ttxz.tar.gz`，需要自己准备并放在构建上下文里：

```bash
docker build -t kaleido-backend:latest .
docker run -d --name kaleido-backend \
  -p 9711:9711 \
  -v $(pwd)/logs:/app/logs \
  -v $(pwd)/storage:/app/storage \
  kaleido-backend:latest
```

如果不想折腾 conda 打包，直接用方式一就行，效果一样。

### Nginx 反代

SSE 必须关掉缓冲，否则前端会等回答全部生成完才一次性显示：

```nginx
location /fijoAi/ {
    proxy_pass http://127.0.0.1:9711/fijoAi/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}
```

- `config.yaml`：模型 API Key、MySQL 账号密码、Milvus 地址、沙箱令牌
- `.env.prod`：生产环境配置
- `.personal-mcp.key`：MCP 密钥
- `mp_cookies.json`：登录态 Cookie

建议提交一份 `config.example.yaml` 作为模板，把真实配置留在服务器上，或者用环境变量注入。发布前先执行 `git status` 确认没有把上面这些文件加进去。

## 常见问题

**接口 401 或提示没权限？**
先看登录接口返回的 token 有没有带上，再确认账号所属公司、用户组是否被授权了对应技能组和知识库。

**知识库上传成功但搜不到？**
多半是 Milvus 连接或者向量维度配置不对。可以调用知识库的同步接口修复 MySQL 和 Milvus 的数据，再重试。

**回答一直转圈不出字？**
检查 Nginx 是否关了 `proxy_buffering`，以及请求是不是走了非 SSE 的转发链路。

**沙箱执行报连接失败？**
`config.yaml` 里的 `sandbox.url` 要能访问到 Kernel 网关，没配沙箱时，涉及代码执行的技能会失败，但不影响纯知识库问答。
